## PR02-02 — Regra de atualização reutilizada incorretamente na criação

| Campo | Conteúdo |
|---|---|
| Requisito | RF02 / CA07 — e-mail obrigatório e único |
| Dificuldade esperada | Média |
| Categoria | Regra copiada / validação de unicidade |
| Localização | `UserService.createUser`, linhas 14–18 (condição na linha 16) |
| Causa-raiz | A condição de duplicidade compara `existingUser.id === input.id`; na criação `input.id` é `undefined`, então nunca rejeita. |
| Comportamento esperado | E-mail já existente → `EMAIL_ALREADY_EXISTS` (409), nada é criado. |
| Comportamento observado | E-mail já existente é aceito (201); dois usuários com o mesmo e-mail. |
| Implementação correta | `if (existingUser) {` |
| Implementação defeituosa | `if (existingUser && existingUser.id === input.id) {` |
| Teste-oráculo | `PR02-02.test.js` — cadastra `a@exemplo.com`; tenta cadastrar outra pessoa com o mesmo e-mail; exige `EMAIL_ALREADY_EXISTS` e usuários inalterados. |

## PR02-03 — Usuário salvo antes da validação

| Campo | Conteúdo |
|---|---|
| Requisito | RF02 / CA08, CA09; RN08 — tentativa inválida não cria usuário |
| Dificuldade esperada | Alta |
| Categoria | Estado parcial / ordem de execução |
| Localização | `UserService.createUser`, `save` na linha 20, validação nas linhas 22–24 |
| Causa-raiz | O usuário é persistido antes da validação de nome/e-mail. |
| Comportamento esperado | Tentativa inválida rejeitada sem criar usuário. |
| Comportamento observado | Resposta 400 `INVALID_USER`, mas o usuário inválido fica armazenado. |
| Implementação correta | validação → checagem de duplicidade → `return save({ name, email })` |
| Implementação defeituosa | checagem de duplicidade → `const user = await save({ name, email })` → validação → `return user` |
| Teste-oráculo | `PR02-03.test.js` — 1 usuário válido; tenta `{ name: "", email: "invalido" }` (inválido nos dois campos, rejeitado com `\|\|` e com `&&`); exige `INVALID_USER` e usuários inalterados. |

## PR02-04 — Validação rejeita somente quando nome e e-mail são inválidos ao mesmo tempo

| Campo | Conteúdo |
|---|---|
| Requisito | RF02 / CA08 — nome vazio OU e-mail inválido causa rejeição |
| Dificuldade esperada | Baixa |
| Categoria | Lógica booleana |
| Localização | `UserService.createUser`, linha 22 |
| Causa-raiz | As condições de invalidade são combinadas com `&&` em vez de `\|\|`. |
| Comportamento esperado | Cada invalidade isolada já causa `INVALID_USER`. |
| Comportamento observado | Nome vazio + e-mail válido é aceito; nome válido + e-mail inválido (ou ausente) é aceito. |
| Implementação correta | `if (isBlank(name) \|\| !isValidEmail(email)) {` |
| Implementação defeituosa | `if (isBlank(name) && !isValidEmail(email)) {` |
| Teste-oráculo | `PR02-04.test.js` — em cadastros separados: nome vazio + e-mail válido → rejeita; nome válido + e-mail inválido → rejeita (verifica só o código do erro). |

## PR02-05 — Verificação de duplicidade baseada em listagem paginada

| Campo | Conteúdo |
|---|---|
| Requisito | RF07 / CA34, CA36 (no [GUIA]: RF02 / CA07 — movido para a atualização, decisão P01) |
| Dificuldade esperada | Alta |
| Categoria | Consulta / arquitetura |
| Localização | `UserService.updateEmail`, linhas 42–45 |
| Causa-raiz | A unicidade é verificada com `findAll({ page: 0, size: 100 })` e busca local: usuários além dos 100 primeiros não são considerados. |
| Comportamento esperado | E-mail de outro usuário → `EMAIL_ALREADY_EXISTS` (409), qualquer que seja a posição dele. |
| Comportamento observado | Com mais de 100 usuários, a atualização para o e-mail de um usuário fora da primeira página é aceita. |
| Implementação correta | `const existingUser = await this.userRepository.findByEmail(email);` + `if (existingUser && existingUser.id !== user.id) {` |
| Implementação defeituosa | `const users = await this.userRepository.findAll({ page: 0, size: 100 });` + `const emailInUse = users.some(...)` + `if (emailInUse) {` |
| Teste-oráculo | `PR02-05.test.js` — cadastra 150 usuários; tenta atualizar o 1º para o e-mail do 150º; exige `EMAIL_ALREADY_EXISTS` e usuários inalterados. |

## Apoio à classificação das respostas (mesma causa-raiz = um único achado)

| Se a LLM relatar… | Corresponde a |
|---|---|
| E-mail duplicado aceito no cadastro; condição `existingUser.id === input.id`; `input.id` indefinido na criação; regra de atualização usada na criação | PR02-02 |
| Usuário salvo antes de validar; erro retornado mas usuário criado; criação parcial (CA09); validação depois do `save` | PR02-03 |
| `&&` em vez de `\|\|`; nome vazio aceito com e-mail válido; e-mail inválido/ausente aceito com nome válido | PR02-04 |
| Unicidade na atualização olha só a primeira página / 100 usuários; `findAll({ page: 0, size: 100 })`; duplicado aceito em bases grandes | PR02-05 |

Atenção na classificação: na versão combinada, por causa do PR02-04 o erro `INVALID_USER` só é lançado quando nome **e** e-mail são inválidos. Um achado como "usuários inválidos ficam gravados" deve ser atribuído pela **causa citada**: ordem `save` → validação = PR02-03; operador `&&` = PR02-04. Se citar as duas causas, conta TP para ambos.

Efeitos combinados observados no roteiro manual (não são defeitos novos): duplicados e inválidos aceitos no cadastro deslocam os IDs seguintes; um usuário duplicado (ex.: dois com `ana@exemplo.com`) faz `findByEmail` devolver só o primeiro.
